# 避雷平台产品需求文档

版本：v0.1 ｜ 日期：2026-10-15 ｜ 状态：产品范围草案，可用于原型与开发评估

本地第一版的统一完工标准、验收状态及待决策事项见 [acceptance.md](acceptance.md)。本文保留详细产品规则；建议方案不因汇总自动成为已确认决定。

> 本文将已经确认的需求与建议方案分开。文中的“建议”不是已确认决定；未确定的事项集中在末尾。本文不代表平台已经上线，也不代表已有审核团队或自动核验能力。

## 1. 产品定位与目标

面向全国的用户经历社区，帮助用户在求职、消费、旅游等决策前，集中找到具体对象的踩雷经历、相关材料、异议及后续处理结果。

核心问题：负面体验容易被大量好评淹没，用户难以发现问题、判断依据和追踪后续变化。

产品价值：让问题容易找到、依据可以查看、争议可以补充、结果持续更新。平台不把投稿、点赞或材料数量直接视为事实成立。

第一版不做商业化。先验证是否有人发布真实经历、是否有人在决策前搜索，以及追踪更新是否有用。暂无增长或收入数值目标，待试用基线建立后再定。

## 3. 用户与权限

| 角色 | 能力与限制 |
| --- | --- |
| 访客 | 建议可浏览、搜索公开内容；发布、关注、互动前登录 |
| 普通用户 | 发布经历或求助，提交材料、异议、举报，关注对象和帖子 |
| 作者 | 更新自己的帖子，回应补充或异议；不能删除他人的贡献 |
| 对象代表 | 在核验代表身份后，以标识身份回应或申诉；无权直接修改用户内容 |
| 审核人员 | 审核内容和材料，处理举报、申诉、对象合并与状态变更，操作留痕 |
| 管理员 | 管理类别、权限和规则；敏感数据访问需要单独授权并记录 |

对外匿名仅隐藏公开身份，不表示平台不保存账号记录。匿名内容的接口、图片地址和页面数据均不得暴露作者账号。对象代表的身份核验与其回应是否属实是两件事，不得混为一种认证。

## 4. 第一版范围与优先级

### 4.1 P0：首轮试用必须具备

- 账号、昵称/匿名发布，以及基础个人中心。
- 固定类别、对象创建与查找、对象汇总页。
- 经历帖发布与修改、图片材料、证据状态标签。
- 全国搜索，按类别、城市、问题类型、发生时间筛选。
- 城市浏览；取得定位授权时浏览附近，拒绝定位后可手动选城市。
- 求助帖及其回应，求助不能自动计入对象的经历统计。
- 独立经历、补充佐证、提出异议及其审核。
- 后续更新时间线，关注帖子/对象，站内更新通知。
- 对象代表回应、举报、申诉与人工审核后台。
- 隐私提示、材料访问控制、状态变更与审核操作记录。

### 4.2 P1：试用后再做

- 地图浏览、收藏清单、跨对象对比、更细的产品/服务结构。
- 更多订阅渠道、可配置的更新摘要。
- 辅助发现重复材料、批量灌水和隐私信息的自动工具。
- 新类别申请的完整自助流程；P0 可由运营人工处理申请。

### 4.3 第一版不纳入

- 普通个人档案、私信、交易、广告、付费删帖、自动裁定事实真伪。
- 按“最差”排名的全国黑榜、未经核验的风险分或可信度分。
- 全网抓取和搬运差评、复杂推荐算法、外部实时数据同步。

P0 功能较多，可按第 15 节分阶段交付；在审核与举报流程未就绪前，不开放全国公众自由投稿。

### 4.4 国际化（i18n，已排后续）

2026-10-16 用户要求加入 i18n，允许后续实施，当前先记录需求、不立即改造现有界面。

- 界面文案、分类/状态标签及面向用户的系统消息支持多语言；用户发布的正文、对象名称和材料不自动翻译，不因此改变原始内容。
- 提供语言选择、系统语言匹配、偏好保存和缺失翻译回退；日期、时间、数字等按所选区域格式展示，同时保留发生时间精度和“大致时间”含义。
- 预留可维护的翻译资源、插值与复数等文案组织方式；切换后检查网页/App 布局、长文案和可访问性。
- 首批语言、默认/回退语言、翻译来源，以及首版交付时点待实施前确认；不默认已经完成或自动引入翻译服务。

## 5. 对象与类别设计

对象是经历所指向的公司、门店、景点、产品或服务；帖子是一次具体经历或一个问题。

| 类别 | 建议记录的信息 | 区分规则 |
| --- | --- | --- |
| 公司/用人单位 | 名称、别名、所在城市、地址、可选主体标识 | 同名公司不能自动合并；区分公司主体与办公地点 |
| 饭店 | 店名、品牌、门店地址、城市 | 品牌和门店分开，门店经历不直接归咎于全部分店 |
| 景点 | 名称、地点、运营主体（可选） | 景点与周边店铺分别建档 |
| 其他 | 对象名称、对象类型、可选品牌/型号/地区 | 产品可无固定位置，服务需说明具体范围 |

发布前先搜索已有对象；找不到可提交新对象。疑似重复对象进入人工确认。合并保留旧链接跳转、帖子关联和操作记录；更名、搬迁、换经营主体不能静默覆盖历史。

类别由平台维护，用户申请新增。问题标签随类别变化，例如招聘描述不符、口味体验、排队、收费说明等；这些是分类标签，不是平台作出的事实认定。

2026-10-16 用户确认初始问题类型集合，每帖可多选，后续可调整：

| 对象类别 | 初始问题类型 |
| --- | --- |
| 公司 | 招聘描述、薪酬约定、工作安排、服务体验 |
| 饭店 | 口味体验、收费说明、排队服务、卫生体验 |
| 景点 | 宣传信息、收费说明、设施体验、服务秩序 |
| 其他 | 信息差异、收费说明、服务体验 |

该决定确认分类集合与多选方式；实现与验证见 development.md 第 23 节和 progress.md，不替代尚待确定的严重指控、独立佐证和有效异议判据。

## 6. 经历、求助与材料


### 6.1 经历帖字段

| 字段 | 规则 |
| --- | --- |
| 标题 | 必填，概括具体问题，长度上限待原型确定 |
| 对象 | 必填，一个主对象；搜索选择或申请新建 |
| 发生时间 | 必填，可选择具体日期、月份或自选起止日期范围；范围明确显示为“大致时间” |
| 发布时间 | 系统生成，与发生时间分别显示 |
| 问题类型 | 必填，来自类别下的标签，可多选 |
| 经历正文 | 必填，提示说明经过、实际体验及影响；主观感受与可核实事实分开描述 |
| 亲历声明 | 提交前确认本人参与或直接经历；转述不能冒充亲历 |
| 图片/材料 | 一般可选；特定严重指控进入补充材料流程 |
| 对外身份 | 昵称或匿名，发布前预览 |
| 希望的处理 | 可选，例如说明情况、退款、纠正信息 |

草稿、待审、需补充、已发布、限制展示、已撤回等属于发布生命周期，与证据状态分开存储。

2026-10-16 用户确认时间规则：大致时间通过自选起止日期填写，明确标为“大致时间”；日期筛选时，只要所填时间范围与筛选范围有交集就显示，并保留精度标记。具体日、月份和范围都不能在公开展示中伪装成另一种精度。

### 6.2 求助帖

可以关联具体对象，也可以只选类别和城市。页面明确标识“求助”，不能因提问或猜测生成负面经历统计或证据标签。回应者可以发布并关联自己的亲历帖，也可给出普通回答；普通回答不能直接当作独立佐证。

### 6.3 材料

建议 P0 先支持图片与文字说明。具体图片大小、数量、格式在技术设计阶段确定。每份材料记录来源说明、关联内容、提交者、提交时间、审核状态及可见范围。

上传时提供“公开展示”和“仅供审核”的选择。公开展示使用脱敏副本；原文件受限访问。页面不能因为存在仅供审核材料就宣称已证实。用户不得通过公共地址绕过权限获取原文件。

对无材料的普通体验可发布“仅本人陈述”；严重指控的适用规则、补充要求、审核时限和处理人员必须在开放投稿前明确，不能交给开发者自行猜测。具体哪些陈述需要升级审核属于待决策项。

## 7. 证据状态标签

标签表达当前材料状态，不是事实裁决，也不等于对象整体可靠程度。以单篇经历为基础，不给整个商家或公司生成一个统一“可信”标签。

| 标签 | 建议颜色 | 含义 | 触发条件 |
| --- | --- | --- | --- |
| 仅本人陈述 | 灰色 | 尚无展示出的支持材料 | 已发布经历但无审核通过的关联材料 |
| 已附材料 | 蓝色 | 已提交并通过基础检查的相关材料 | 材料可读、相关且完成隐私检查；不表示真实性已经核实 |
| 有独立佐证 | 青色 | 有其他用户提交的相关独立资料/经历 | 经人工检查相关性及独立性后标记；资料数量本身不触发 |
| 存在争议 | 橙色 | 存在与关键陈述相关的有效异议 | 异议材料经审核后进入讨论状态；仅点击反对不能触发 |

以上配色和触发细则为建议。所有颜色同时配文字，不能只靠颜色辨认；对比度在界面验收时检查。

### 7.1 并存与变化

- 建议使用“基础材料状态＋争议标签”：基础状态显示上述前三种之一，“存在争议”可同时展示。例如“有独立佐证 · 存在争议”。
- 基础状态显示当前最充分的状态，但详情页始终能查看材料数量、来源、审核说明和变更历史。
- 点赞、浏览量、评论数、账号数量均不直接提升状态。
- 同一张截图重复上传、转发同一来源，不算多份独立佐证；无法确认独立性时保留材料，但不提升标签。
- 佐证涉及一个问题时，不能推导为整篇所有说法成立；记录材料具体支持或反对的陈述。
- 关键材料失效、撤回或发现重复时，重新评估当前标签，记录原因并通知已关注用户。
- 标签变更由审核人员确认；第一版不依靠自动算法判定真假。

## 8. 其他用户如何参与

1. **我也遇到过**：创建独立亲历帖，关联同一对象及原帖，写清自己的发生时间与经过。独立经历不自动证明原事件发生过。
2. **补充佐证**：指明支持原帖哪项陈述，说明材料来源，可上传材料。
3. **提出异议**：指明反对或需修正的陈述，提供理由及可选材料；有效异议需审核后才能改变争议标签。
4. **有帮助**：表达阅读价值，不影响证据状态。
5. **举报**：处理隐私、冒充、无关内容等规则问题，区别于对事实提出异议。

补充和异议均有自己的状态与版本。作者可以回应，不能自行删除他人的有效异议；涉及违规内容由平台处理。

## 9. 后续追踪与反转

### 9.1 两类关注

- 关注帖子：接收该事件的重要更新。
- 关注对象：接收该对象新发布的经历及重要进展，建议聚合提醒，避免刷屏。

第一版建议仅使用站内通知；不默认开启短信、邮件等渠道。定位和通知授权分开，退出关注立即停止后续提醒。

### 9.2 事件时间线

可记录作者补充、代表回应、佐证、有效异议、标签变化、申诉结果、作者更正、材料失效及处理进展。每条记录含时间、操作者角色、类型、摘要、关联内容和版本。

必须区分：

- 事实变化：原陈述被补充、修正，或仍存在争议。
- 处理变化：协商中、对方已回应、作者报告已解决等。

“已退款”不能自动等同于原陈述错误；“当事方反对”不能自动等同于反转；“作者报告已解决”也不代表所有人认可。

### 9.3 反转展示规则

- 不设由点赞触发的“已反转”结论。用明确更新标题描述实际变化，例如“作者更正发生时间”“关键材料被撤回”。
- 影响主要判断的更正置顶在详情页，并同步更新列表卡片摘要、对象页和搜索结果中的相关状态。
- 保留可公开的历史版本和更正原因；涉及隐私或违规内容时不继续公开原始敏感信息，但保留受限审计记录。
- 重大更新向关注者发送一次通知；同一事件重复处理不得重复发送。
- 原文修改不能静默抹去已存在的异议；异议与其对应的历史版本保持关联。

## 10. 页面与主要流程

| 页面 | 主要内容与操作 |
| --- | --- |
| 首页/城市浏览 | 搜索入口、类别、城市选择、最新经历和求助 |
| 搜索结果 | 对象与帖子分组，筛选类别/城市/问题/发生时间，标明更正和争议 |
| 对象页 | 名称与地址、对象关系、相关经历、问题分布、求助、后续更新、关注 |
| 经历详情 | 发生时间、发布身份、证据标签、正文、材料、重要更正、时间线、佐证/异议/举报 |
| 求助详情 | 问题、关联对象、回答、关联亲历帖 |
| 发布页 | 内容类型、对象选择、时间、正文、材料、匿名设置、提交预览 |
| 消息中心 | 关注更新、审核结果、补充要求、申诉处理 |
| 我的 | 帖子、草稿、贡献、关注、通知设置 |
| 对象代表入口 | 代表身份申请、回应、申诉与处理状态 |
| 管理后台 | 待审队列、材料脱敏、举报/申诉、对象合并、标签与权限、操作日志 |

建议默认按发布时间展示，提供发生时间排序；“有帮助”可作为用户选择的排序方式，不决定事实成立。附近排序仅适用于有有效地点的对象，不展示用户住所或精确行动轨迹。

主要路径：搜索对象 → 看汇总 → 看具体经历及材料 → 检查异议和后续 → 关注；发布经历 → 审核 → 公开 → 收到补充/异议 → 更新；申诉 → 平台审查 → 记录处理理由 → 同步相关页面和通知。

## 11. 审核、申诉与内容边界

目前没有确定审核团队。以下是建议的起步方案，也是公开投稿前需要落实的运营条件：小范围邀请试用、人工先审后发、按处理能力逐步开放。

- 经历、公开材料、重要补充、异议和代表回应均进入对应审核队列。第一版无需自动内容判定即可运行。
- 审核结果：通过、要求修改/补充、拒绝，并提供原因；处理时限待人员安排后确定，不预设无法兑现的承诺。
- 举报记录目标内容、原因、说明、材料、处理状态和决定；紧急隐私问题允许先限制展示，再核查。
- 申诉人可质疑事实、身份或平台决定；平台允许补充材料及复核，保留理由和结果。
- 申诉不自动删帖，不因当事方付费或身份而改变规则。
- 删除公开内容与删除所有内部记录是不同操作；资料保留、账号注销、撤回及备份清理规则上线前制定。
- 不支持曝光私人联系方式、住址、证件等；不支持无关辱骂、威胁或冒充身份。
- 内容数量不代表对象整体质量。对象页只统计当前可公开经历，并标明时间范围与样本数，不推断未投稿用户的体验。

## 12. 数据模型建议

| 实体 | 核心字段/关系 |
| --- | --- |
| User | 账号、公开昵称、状态；匿名映射独立控制访问 |
| Category | 名称、父级、可用问题标签、状态 |
| Subject | 对象类型、名称、别名、类别、城市、可选位置/主体标识、父对象、状态 |
| Post | 经历/求助、作者、公开身份模式、对象、发生时间精度、正文、问题标签、发布状态、版本 |
| Evidence | 所属帖子/贡献、提交者、来源说明、支持/反对陈述、材料文件、公开范围、审核状态 |
| Contribution | 独立经历关联/佐证/异议/回答、提交者、目标版本、审核状态 |
| EvidenceStatus | 基础状态、争议状态、关联材料、变更理由、审核者、时间 |
| ProgressEvent | 更新类型、关联帖子与版本、摘要、事件时间、公开范围 |
| SubjectRepresentative | 账号、对象、核验状态、权限有效期 |
| Response / Appeal / Report | 目标、提交者、说明、材料、处理状态及决定 |
| Follow / Notification | 关注目标、订阅状态、更新事件、去重键、已读状态 |
| Moderation / AuditLog | 操作者、目标、动作、前后状态、原因、时间 |

匿名发布、证据状态、发布生命周期和处理进度必须分别建模，不能共用一个 status 字段。公开查询必须统一排除未通过审核或无权限内容，搜索索引和缓存也遵循相同规则。

## 13. 基础质量要求

- App 第一版同时支持安卓和苹果，核心功能范围一致；配套网页适配手机和电脑。已采用 Expo / React Native 与 React 网页，技术方案见 development.md。
- 网页功能范围建议先覆盖搜索、查看对象/帖子和打开分享链接；完整发布与互动能力是否同步提供，待确认。后台需要独立的管理入口。
- 无定位权限仍可按城市使用；全国性产品或线上服务不强制要求地理坐标。
- 上传失败可重试，发布重复请求不能生成重复帖子；草稿避免意外丢失。
- 后台与普通用户权限隔离，敏感材料访问留痕；文件链接需服从访问权限。
- 标签颜色辅以文字；表单错误明确定位到字段。
- 限制重复提交、刷赞和批量上传；具体阈值可配置，不把账号数量当成独立性证据。
- 内容下架、更正、对象合并后，详情页、列表、搜索索引和缓存状态保持一致。
- 数据备份和恢复需要验证；性能及容量目标待试用规模明确后制定。

## 14. 核心验收场景

| 场景 | 验收结果 |
| --- | --- |
| 发布普通无图亲历 | 正确填写后进入审核，通过后显示“仅本人陈述” |
| 上传支持材料 | 审核前不提升状态；通过后显示“已附材料”，不会显示“已证实” |
| 第三人重复上传相同截图 | 不自动变成“有独立佐证”，记录重复来源 |
| 第三人发布另一独立经历 | 关联对象及原帖，不自动证明原事件；需检查相关性再决定标签 |
| 有效异议与佐证并存 | 同时显示基础状态与“存在争议”，详情可查双方依据 |
| 多人点赞或点击反对 | 不改变证据状态 |
| 严重指控缺少必要材料 | 进入需补充流程，不能绕过规定公开 |
| 作者对外匿名 | 页面、接口和材料公开信息不能透露账号或真实身份 |
| 作者补充已退款 | 生成进度事件，保留原经历，不自动标记为原帖失实 |
| 关键内容被更正 | 详情置顶更正，列表/搜索摘要同步，关注者收到一次重要更新 |
| 关键材料撤回 | 重新评估状态，记录变化及原因，失效内容不继续计入依据 |
| 提交申诉 | 产生可追踪记录，不自动删帖；处理后显示适当的理由及结果 |
| 私密材料被请求 | 普通用户无法通过页面或文件地址读取，授权访问有日志 |
| 拒绝定位 | 可选城市继续搜索与浏览 |
| 同名或连锁门店 | 能区分对象，单店事件不自动扩散到全部门店 |
| 取消关注 | 不再产生该订阅的新通知 |
| 内容下架/对象合并 | 相关列表、统计、搜索与链接按规则更新，无旧敏感内容残留 |

以上作为实现后的验收要求，不表示当前已开发或测试通过。

## 16. 试用期观察指标

- 搜索后找到相关对象/经历的比例、无结果查询及重复对象比例。
- 有效投稿人数、发布完成率、审核通过与补充材料的比例。
- 材料可用性、独立佐证与有效异议数量，重复材料情况。
- 从提交到审核、举报和申诉处理的耗时。
- 关注后收到重要进展的比例、通知重复率和退订反馈。
- 用户是否认为内容帮助了实际决策，以及哪些信息仍不足。

不得将负面帖数量或互动热度当作唯一成功指标。暂不设固定目标值。
