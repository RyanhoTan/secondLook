# 避雷平台开发方案 v0.1

日期：2026-10-15。面向个人开发；配合《避雷平台产品需求文档 v0.1》使用。

统一的本地第一版范围、逐项完成条件与状态见 [acceptance.md](acceptance.md)。阶段交付不等于整个项目完工。

## 1. 本阶段做到什么

项目由 AI 负责技术实现、代码 review、测试与缺陷修复，用户负责产品取舍与体验反馈。用户熟悉 TypeScript、React Native、React、Vue，后端刚入门；技术选择不以用户能否手写实现为限制，但交付仍需便于用户理解和启动。本阶段只要求电脑本地启动、手机能访问、代码可上传 GitHub；不部署公网，不产生服务订阅费用，不上架应用商店。

最终产品目标仍为安卓、苹果 App 和配套网页。先实现最小闭环，再补足完整需求。本文的阶段拆分不删除产品需求。

已有 iPhone，尚未确认 Mac 和安卓测试设备。iPhone 先通过 Expo Go 调试；安卓先使用可用的模拟器或真机，没有完成设备测试时必须记录为未验证。

## 2. 技术选型

| 部分 | 选型 | 理由 |
| --- | --- | --- |
| App | Expo + React Native + TypeScript + Expo Router | 延续已有 RN 基础，先用 Expo Go 跑通手机开发 |
| 用户网页 | React + Vite + TypeScript + React Router | 与已有 React 基础一致，优先做搜索、详情与分享链接 |
| 管理后台 | 同一网页工程内的 /admin 路由 | 减少工程数量；权限仍必须由服务端检查 |
| API | Node.js + Express + TypeScript | 满足本地单体 API 需求；通过统一模块结构约束实现，不为 AI 开发额外增加框架复杂度 |
| 数据库 | SQLite + Prisma | 无需安装独立数据库服务；通过迁移维护结构 |
| 输入校验 | Zod | 校验 API 输入，并共享可公开的数据结构 |
| 图片 | 电脑本地目录 | 不接云存储；公开副本与私有原件分开 |
| 前端请求 | fetch 封装 | 暂不引入全局状态库或复杂请求框架 |
| 工程管理 | npm workspaces，一个 Git 仓库 | 集中管理 App、网页、后端及共享类型 |
| 验证 | Vitest + Supertest；网页关键流程使用 Playwright；App 做设备/模拟器验证 | AI 编写并运行有意义的自动测试，执行可访问环境中的交互验证；设备能力不足时明确未验证部分 |

初始化时使用当时稳定、互相兼容的版本，记录实际 Node 和依赖版本，提交 package-lock.json。Expo 相关依赖通过其推荐安装方式匹配 SDK，不在本文凭空固定版本号。

不先引入 Docker、Redis、微服务、云数据库、搜索集群或 Kubernetes。SQLite 仅按本地单机开发设计；未来部署与扩容时另做容量评估。

## 3. 本地连接方式

```text
iPhone Expo Go / 安卓 App ─┐
                          ├─→ Express API :3000 → SQLite
React 网页 :5173 ─────────┘                    → 本地图片
管理后台 /admin ──────────┘
```

- App 与网页访问同一个 API，共用账号和内容，不通过 GitHub 存业务数据。
- 电脑浏览器可访问 localhost；手机访问电脑的局域网 IP，例如 http://192.168.x.x:3000。
- 手机与电脑先连接同一局域网。API 需要监听可被局域网访问的地址，防火墙仅开放开发所需连接。
- 当前 Expo 官方文档要求：实体 iPhone 上用 Expo Go 打开项目时，电脑 Expo CLI 与手机 Expo Go 登录同一个 Expo 账号。把账号准备和扫码连接纳入环境搭建步骤。
- Expo 开发服务与业务 API 是两套服务；Expo 隧道可用不代表 API 也能被手机访问。第一阶段优先排查局域网连接。
- App 的 API 地址用 EXPO_PUBLIC_API_URL；网页用 VITE_API_URL。这些会进入客户端，不得存密码或密钥。
- 网页分享链接初期只在相应本地环境可用。上传 GitHub 后不会自动变成任何人可访问的网站。
- Expo Go 用于原型和初步设备测试；遇到其未包含的原生能力时再切换 development build。它不等于可上架的独立 App。
- 远程推送、独立安装包、签名与商店发布不属于当前验收。以后需要时单独确定构建环境与账号要求。

## 4. 仓库结构

```text
apps/
  mobile/                 # Expo App
  web/                    # React 网页与后台
  api/
    src/
      routes/             # 接口与中间件
      auth.ts             # 密码与会话规则
      posts.ts            # 公开内容映射与审核事务
      db.ts               # 数据库连接
    prisma/               # schema、迁移、虚构种子数据脚本
packages/
  contracts/              # 可公开的请求/响应结构、Zod 校验、枚举
docs/                     # 需求、方案、决策记录
README.md
.env.example
.gitignore
package-lock.json
```

共享类型、校验和请求工具，先不强行共用网页与 App 的界面组件。Prisma 模型仅留在服务端，不能直接当成公开 API 返回值。

本地数据库与上传目录放在 apps/api 的运行数据目录中并加入 .gitignore。实际路径由配置确定。

## 5. 第一条开发闭环

登录 → 搜索或新建对象 → 发布亲历帖 → 管理员审核 → 网页/App 可查 → 关注 → 作者提交更新 → 审核后出现站内通知。

这一条走通后，再加入佐证、异议、对象代表及申诉。初期只做一个类别的界面联调即可，但数据结构从开始就支持四个初始类别。

## 6. 核心数据表

| 表 | 必要数据 |
| --- | --- |
| User | id、登录名、密码哈希、昵称、角色、账号状态 |
| Session | 随机令牌的哈希、userId、过期时间、撤销时间 |
| Subject | id、类别、对象类型、名称、城市、可选地址/位置、父对象、状态 |
| Post | id、作者、对象、经历/求助、匿名模式、当前公开版本、发布状态 |
| PostRevision | 帖子、标题、正文、发生时间及精度、问题标签、提交时间、审核状态 |
| Evidence | 提交者、关联版本/贡献、支持或反对的具体说法、来源说明、可见范围、文件关联、审核状态 |
| File | 存储键、真实类型、大小、公开脱敏副本键；不对外暴露原文件路径 |
| Contribution | 帖子及目标版本、类型、内容、关联独立经历、审核状态 |
| EvidenceAssessment | 当前基础标签、是否争议、所依据记录、审核者、原因、时间 |
| TimelineEvent | 对象/帖子、事件类型、摘要、关联版本、时间、公开范围 |
| Follow | 用户、目标类型、目标 id；同一用户/目标唯一 |
| Notification | 接收用户、事件、已读时间；用户/事件唯一，防止重复 |
| Representative | 用户、对象、身份核验状态 |
| Case | 举报/申诉、目标、说明、处理状态、决定与理由 |
| ModerationLog | 操作者、目标、动作、前后状态、理由、时间 |

回复/回应可复用贡献结构，类别和问题标签单独维护。具体字段以 Prisma schema 为准，开发前补齐关联、索引与删除规则。

注意：匿名只是公开展示方式。作者 userId 留在服务器中；公开返回通过专门 DTO 隐藏。求助不参加负面经历统计。发生日期使用 date/月份及精度字段，操作时间统一存 UTC，显示时再转换。

## 7. 状态与业务规则

### 发布状态

```text
草稿 → 待审核 → 已发布
             → 需补充 / 拒绝
已发布 → 撤回 / 限制展示
```

编辑已发布内容时新建待审版本，旧公开版本继续展示；新版本审核通过后切换。隐私等需立即处理的问题可以先限制展示。新版本、当前公开版本和审核历史分开保存。

### 证据状态

- 基础标签：仅本人陈述（灰）/ 已附材料（蓝）/ 有独立佐证（青）。
- “存在争议”（橙）单独保存，可与基础标签并存。
- 点赞、材料数量、评论数量不自动改变状态；第一版由管理员根据规则评估。
- 接受普通上传不等于真实性核实；重复来源不计为独立佐证。
- 材料撤回、版本更正或有效异议发生时，标记需要重新评估；审核决定与公开标签同时提交，不留下静默失效的标签。
- 标签、版本和处理进度分开。“作者报告已退款”是进度，不是事实被推翻。

### 事务与通知

审核通过、更换公开版本、写时间线和创建站内通知在同一数据库事务内完成。通知按接收者和事件去重。初期打开消息页或 App 回到前台时刷新，不接远程推送。

## 8. API 约定与接口清单

统一前缀 /api/v1；列表使用 page/limit（服务端设置上限），返回 items/total/page；默认按发布时间与 id 稳定排序。错误返回 code/message/fieldErrors，不泄露数据库错误和文件路径。

| 模块 | 第一批接口 |
| --- | --- |
| 登录 | POST /auth/register、/auth/login、/auth/logout；GET /me |
| 对象 | GET /subjects、/subjects/:id；POST /subjects |
| 帖子 | GET /posts、/posts/:id；POST /posts；PATCH /posts/:id；POST /posts/:id/submit |
| 更新 | POST /posts/:id/updates；GET /posts/:id/timeline |
| 关注 | PUT /follows、DELETE /follows/:id |
| 通知 | GET /notifications；PATCH /notifications/:id/read |
| 审核 | GET /admin/reviews；POST /admin/reviews/:id/decision |
| 后续扩展 | /uploads、/contributions、/reports、/appeals、/representatives |

修改帖子只创建或修改作者自己的待审版本。提交发布时检查必填字段和类别规则。具体接口请求/响应在实现该模块前写入 contracts，避免先列出大量未实现接口。

搜索第一版用参数化查询按名称/别名/标题/正文匹配，再加类别、城市、时间筛选；不接外部搜索服务。仅查可公开内容。附近功能后置，可先用手动城市选择跑通列表。

## 9. 登录、匿名与文件权限

- 本地开发使用登录名＋密码，不接短信、第三方登录和真实身份核验服务。密码用成熟密码哈希实现，不自行设计算法。
- 建议使用可过期、可撤销的随机会话令牌，数据库仅存令牌哈希。App 存储使用兼容所选 Expo SDK 的安全存储；网页先存在内存，刷新后重新登录，后续再优化持久登录。
- 服务端校验角色、资源所有权和公开范围；前端隐藏按钮不是权限控制。
- 对外匿名的公开内容不返回作者 id、登录名或可关联账号的字段；作者本人和授权后台使用单独接口。
- 私有原件不能挂到静态目录。通过鉴权文件接口读取；对外只提供经审核的脱敏副本。
- 图片检查真实格式、大小、数量，生成随机文件名，清理位置等元数据；公开前确认隐私遮挡。具体限制作为配置集中维护。
- 开发管理员由种子脚本创建，密码从本地环境传入；普通注册不能指定管理员角色。

## 10. 分阶段任务与完成条件

| 顺序 | 工作 | 完成条件 |
| --- | --- | --- |
| 1 | 初始化仓库、版本与环境说明、数据库迁移和虚构数据 | 新电脑按 README 可初始化；Web、API、Expo 启动 |
| 2 | 手机连 API、账号与权限 | iPhone 可访问健康检查、登录；普通用户无法调用后台 |
| 3 | 对象、经历、审核、搜索 | App 投稿，网页后台审核，两端均可查看；未审内容查不到 |
| 4 | 版本更新、时间线、关注与通知 | 更正后新版本生效，历史可追踪，通知不重复 |
| 5 | 图片、佐证、异议与标签 | 私有文件不外泄；重复资料不自动升级；争议可并存 |
| 6 | 求助、城市/附近、代表回应、举报申诉 | 类型与权限正确，后台能处理完整案例 |
| 7 | 安卓/iPhone 联调、README 和 GitHub 整理 | 记录实际设备及结果；无账号秘密、私人材料或运行数据入库 |

每阶段能跑再进入下一阶段，不先做完整视觉装修。现阶段不估算固定工期；根据实际完成速度再排期。

## 11. AI 开发、review 与测试流程

每次按一个可验收的功能闭环交付，不一次生成全部模块。流程为：

1. 从需求中列出本次行为、接口、权限和失败场景；若有产品歧义先向用户确认，常规实现取舍由 AI 决定并记录。
2. 编写迁移、业务逻辑与界面；优先在 services 中集中规则，路由只负责校验、鉴权与调用，避免两端各自实现证据判定。
3. 根据需求和失败场景编写关键测试并实际运行；接口集成测试使用独立临时数据库，不修改用户本地数据。网页闭环使用浏览器自动化验证。
4. 单独进行 review，检查当前改动及其关联流程，重点查权限、匿名泄露、状态不一致、文件访问、事务及回归；不能只重复实现者的解释，也不能把测试全绿等同于 review 通过。
5. 修复发现的问题，重跑受影响的测试；完成类型检查与适用的构建检查，再交付本次结果。
6. 报告实现内容、实际执行的命令与结果、review 发现及处理、仍未验证的环境。未运行的检查不能写成通过。

Review 检查清单和验收场景先于实现确定，避免测试只是在复述代码。开发、review 和测试均可由 AI 完成，不把日常检查转交给用户。用户主要确认产品效果、必要账号和设备访问等外部条件。

每个功能的完成标准：需求行为已实现；关键权限与失败场景覆盖；检查实际通过；无尚未处理的阻断问题；文档与代码一致。若缺少设备、服务或访问权限，则报告可交付部分与阻塞项，不能宣称整个功能已验证完成。

### 必须验证的地方

自动测试集中在高影响规则：匿名 DTO 不泄露身份；普通用户不能审帖或改他人内容；未审/下架内容不出现在搜索；私有文件越权被拒；佐证与争议正确并存；更新失败事务回滚；通知唯一。

交互验证：安卓与 iPhone 的登录、上传、发布、详情、返回与刷新；网页分享路由直达；拒绝定位可选城市；手机网络断开有提示；更正后的卡片和详情一致。AI 在可访问的浏览器、模拟器或设备环境中执行；用户拥有 iPhone 不等于 AI 已获得控制设备的能力，没有测试条件的部分明确记为未验证。

本地只用虚构公司、饭店和景点、虚构用户及材料进行测试。README 给出从空数据库开始的验证路径，不把演示数据写成真实投诉。

## 12. GitHub 交付

提交源码、迁移、虚构种子数据脚本、依赖锁文件、.env.example、需求和开发文档。

忽略 .env、本地数据库及 journal/WAL 文件、上传材料、日志、会话文件、node_modules、构建输出、签名证书和凭据。上传前检查暂存文件列表。

README 至少写清：项目状态、实际版本、安装与迁移、各端启动命令、局域网配置、测试账号生成方式、已完成/未完成列表、测试方法。运行命令以实际 package.json 为准，不在尚无代码时声称已有脚本。

GitHub 公开仓库与私有仓库由你决定，许可证也需另选；本方案不代替创建仓库、推送或授权发布。

- 公开运营需要的审核责任、严重指控边界与处理规则：本地用模拟案例验证，正式开放前另行落实。

当前已创建工程，并实现本地文字投稿、人工审核、搜索查看、关注和进展通知的最小闭环。完整产品尚未实现；实际验证结果与下一阶段见 progress.md。

## 14. UI 规范

用户明确要求依据 apple-design 技能实施简约界面与深浅色模式。完整技能内容见 design/apple-design-skill.md，产品中的具体规则与验收清单见 design/ui-spec.md。设计原则以实际可读性、触控反馈、连续交互和可访问性为依据，不以静态圆角或装饰作为验收。
